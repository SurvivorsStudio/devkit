# PR 만들기

작업 중인 변경사항을 **커밋 → AI 리뷰 → PR 생성**까지 진행합니다.

> **머지는 하지 않습니다.** 별도 커맨드입니다. 이 커맨드는 PR 을 여는 것으로 끝납니다.

---

## 1단계 — 사전 확인

```bash
git rev-parse --show-toplevel        # git 레포인지
git status --short                   # 변경사항이 있는지
git branch --show-current
gh auth status
```

기준 브랜치를 확인합니다 (보통 `main`):

```bash
gh repo view --json defaultBranchRef -q .defaultBranchRef.name
```

**변경사항이 없고 미푸시 커밋도 없으면** 여기서 멈추고 사용자에게 알립니다.

## 2단계 — 브랜치

**현재 브랜치가 기준 브랜치(`main`)라면 새 브랜치를 만듭니다.** 묻지 않고 진행하되, 어떤 이름으로
만들었는지는 보고합니다.

이름은 `<type>/<영문-슬러그>` 형태로, **변경 내용에서 유추**합니다:

```
feat/core-storage        새 기능
fix/token-replace        버그 수정
docs/onboarding          문서
refactor/audio-context   구조 변경
```

```bash
git checkout -b <브랜치명>
```

이미 기준 브랜치가 아니라면 **그 브랜치를 그대로 씁니다.** 임의로 새로 만들지 마십시오.

## 3단계 — 논리 단위로 커밋

`git add -A` 로 한 번에 밀어넣지 **마십시오.** 변경사항을 읽고 의도 단위로 나눕니다.

```bash
git status --short
git diff                             # 워킹 트리
git diff --cached                    # 이미 스테이지된 것
```

### 나누는 기준

**파일이 아니라 의도로 나눕니다.** 한 커밋은 하나를 말해야 합니다.

| 좋음 | 나쁨 |
|---|---|
| `feat: storage 모듈 추가` + `docs: storage 사용법 추가` | `feat: storage 추가하고 문서도 고침` |
| `fix: 토큰 치환에서 TEMPLATE.md 제외` + `chore: 의존성 갱신` | 무관한 두 변경이 한 커밋에 |

한 파일 안에서 성격이 다른 변경이 섞였다면 `git add -p` 로 조각을 나눕니다.

### 커밋 메시지 — Conventional Commits

```
<type>[optional scope][!]: <설명>

[본문 — 왜 이렇게 했는지]

[footer]
```

| type | 쓸 때 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서만 |
| `refactor` | 동작 변화 없는 구조 변경 |
| `perf` | 성능 |
| `test` | 테스트 |
| `build` | 빌드 시스템·의존성 |
| `ci` | CI 설정 |
| `style` | 포매팅 (동작 무관) |
| `chore` | 그 외 |

- **설명은 한국어로, 명령형 현재.** "추가함" 이 아니라 "추가"
- **본문에는 무엇이 아니라 왜.** 무엇은 diff 가 말해 줍니다
- 호환성이 깨지면 `feat!:` 또는 footer 에 `BREAKING CHANGE: <설명>`
- 기존 이력의 트레일러 관행을 따릅니다 (`git log -3` 으로 확인)

> ⚠️ **`.env` · 토큰 · 키 · `.claude/settings.local.json` 을 커밋하지 마십시오.**
> 스테이지 전에 `git status` 를 눈으로 확인합니다.

커밋이 끝나면 **어떻게 나눴는지 사용자에게 보고**합니다.

## 4단계 — AI 리뷰

`devkit:pr-reviewer` 서브에이전트를 **동기로** 실행합니다 (결과가 필요하므로 백그라운드 금지).

전달할 것:
- 기준 브랜치 이름
- 이 브랜치에서 만든 커밋 목록
- 리뷰 범위는 `merge-base..HEAD` 전체

리뷰어는 읽기 전용입니다. 코드를 고치지 않고 보고만 합니다.

## 5단계 — 리뷰 결과 처리

### 문제가 없으면

바로 6단계로 갑니다.

### 보완 사항이 있으면

**항목을 그대로 사용자에게 보여준 뒤** 어떻게 할지 묻습니다. 임의로 고치지도, 임의로 넘기지도
마십시오.

```
리뷰에서 N건이 나왔어:

심각 (고쳐야 함)
1. <파일:줄> — <무엇이 잘못됐는지>
   재현: <어떤 상황에서 실패하는지>

보완 권장
2. ...

지금 고칠까, 이대로 PR 올릴까? 항목별로 골라도 돼.
```

`AskUserQuestion` 으로 선택지를 제시합니다 — **지금 고치기 / 이대로 올리기 / 항목별로 선택**.

- **고치기로 하면**: 수정 후 별도 커밋(`fix:` 또는 해당 type)으로 올립니다. 리뷰는 **다시 돌리지
  않습니다** — 한 번만 봅니다. 사용자가 요청하면 그때 재리뷰
- **넘기기로 하면**: PR 본문의 **"알려진 보완 사항"** 절에 그대로 적습니다. 조용히 버리지 마십시오

## 6단계 — 푸시하고 PR 생성

```bash
git push -u origin <브랜치명>
```

PR 본문은 이 구조로 씁니다:

```markdown
## 무엇을

<한두 문장. 왜 이 변경이 필요한지>

## 어떻게

- <커밋 단위로 요약>

## 확인한 것

- <실제로 돌려본 것. 빌드·타입체크·수동 확인>

## 알려진 보완 사항

- <리뷰에서 나왔지만 이 PR 에서 넘긴 것. 없으면 이 절을 지운다>
```

```bash
gh pr create --base <기준브랜치> --title "<제목>" --body "<본문>"
```

제목은 커밋이 하나면 그 메시지를, 여러 개면 전체를 아우르는 한 줄로 씁니다. Conventional Commits
형식을 유지합니다.

## 7단계 — 보고

- PR URL
- 커밋을 몇 개로 어떻게 나눴는지
- 리뷰 결과와 처리 방식 (고침 / 넘김)
- CI 가 돌면 `gh pr checks` 로 확인할 수 있다고 안내

---

## 하지 말 것

- **머지하지 마십시오.** `gh pr merge` 는 이 커맨드의 범위가 아닙니다
- **`git push --force`, `git reset --hard`, `git rebase` 를 쓰지 마십시오.** 남의 커밋과 기록이
  날아갑니다
- **`git add -A` 로 통째로 스테이지하지 마십시오.** 3단계의 요점이 그것입니다
- **리뷰 결과를 요약하거나 걸러내지 마십시오.** 사용자가 판단할 수 있게 그대로 보여줍니다
- **리뷰에서 나온 문제를 묻지 않고 고치지 마십시오.** 5단계에서 확인받습니다
- 기준 브랜치에 직접 커밋하지 마십시오 — 2단계에서 브랜치를 땁니다

## 실패했을 때

| 증상 | 확인 |
|---|---|
| `gh pr create` 권한 오류 | `gh auth status` · 레포 접근 권한 |
| 워크플로 파일 푸시 거부 | 토큰에 `workflow` 스코프 없음 → `gh auth refresh -h github.com -s workflow` |
| `merge-base` 를 못 찾음 | `git fetch origin` 후 재시도 |
| 이미 PR 이 있음 | `gh pr view` 로 확인. 새로 만들지 말고 사용자에게 알림 |
